PHASE 8.5 — CHAT UX AND RESPONSIVE NAVIGATION POLISH

Continue from the existing completed Phase 1–8 implementation.

This is a focused UX improvement pass before the final Phase 9 security/testing phase.

First inspect the actual current codebase and existing routing, authentication, conversation APIs, Firestore conversation model, generated API clients, and responsive layout.

Do NOT restart any previous phase.

Do NOT redesign the application from scratch.

Preserve the existing visual identity, typography, colors, spacing language, responsive design, Firebase authentication, Gemini behavior, Qdrant/memory behavior, agent/tool calling, feedback/adaptation, and existing API architecture.

Only implement the UX improvements described below.

==================================================
1. SIGNUP → CHAT
==================================================

After a successful signup, redirect the newly authenticated user directly to:

/chat

Do not send a newly registered user back to /login or another intermediate screen.

Preserve the existing login behavior.

Do not bypass authentication or protected-route checks.

==================================================
2. CONVERSATION HISTORY OVERFLOW
==================================================

Inspect the current desktop conversation-history panel.

There is currently a visual issue where long conversation titles/questions can extend outside the intended white conversation-history container.

Fix this properly.

Requirements:

- Conversation history must remain visually contained inside its card/panel.
- Long titles must wrap or truncate gracefully.
- Text must never overflow outside the white container.
- The panel should have appropriate scrolling when many conversations exist.
- Individual conversation items should remain clickable.
- The currently selected conversation should remain visually identifiable.
- Do not allow long user-generated text to break the layout.
- Preserve the existing desktop visual style.

Use CSS/layout fixes rather than arbitrary hardcoded truncation that makes titles unusable.

Also verify the layout with long conversation titles.

==================================================
3. EDITABLE CONVERSATION TITLES
==================================================

The current conversation history uses the first user message/question as the conversation title.

Improve this behavior.

Conversation titles must become user-editable.

Requirements:

- Preserve the existing conversation document structure where possible.
- Add the minimum required API/backend support for updating a conversation title if it does not already exist.
- Ownership must be enforced server-side using the authenticated Firebase UID.
- Never trust a client-provided userId.
- Do not allow a user to rename another user's conversation.
- Reuse the existing conversation routes and generated API client patterns.
- Do not create a second conversation system.

UI:

- Add a small edit/pencil control for the current conversation title or conversation-history item.
- Allow the user to enter a custom title.
- Provide save/cancel behavior.
- Show loading/error states.
- Prevent empty/invalid titles.
- Update the UI immediately after successful save.
- Persist the title after refresh.

For newly created conversations, use a sensible short default title rather than automatically treating the entire first user question as the permanent title.

Do not generate titles using another Gemini/AI call.

Keep the implementation deterministic and simple.

==================================================
4. MOBILE NAVIGATION
==================================================

The current mobile layout does not provide the same navigation functionality available on desktop.

Implement a responsive mobile navigation mechanism.

On mobile, users must be able to access:

- Conversations
- Memory
- Sign out

A hamburger/menu button with a drawer or compact navigation panel is acceptable.

Requirements:

- Do not redesign the entire mobile UI.
- Reuse the existing routes.
- Reuse existing authentication/logout functionality.
- Clearly indicate the current section.
- The menu should close after navigation where appropriate.
- It must work on narrow phone widths.
- It must not cover or break the chat composer unnecessarily.

==================================================
5. MOBILE CONVERSATION HISTORY
==================================================

Mobile users must be able to view and switch between their conversations.

Provide an accessible conversation-history view from the mobile navigation.

Requirements:

- Show the user's conversations.
- Allow selecting a conversation.
- Preserve conversation persistence.
- Handle long conversation titles safely.
- Show an appropriate empty state.
- Allow returning to the current chat.
- Do not create a separate mobile-only conversation data source.

Reuse the existing authenticated conversations API.

==================================================
6. MOBILE SIGN OUT
==================================================

Add a visible sign-out action inside the mobile navigation.

Use the existing logout/authentication implementation.

After logout:

- clear authenticated UI state using the existing auth flow
- redirect to the existing login route
- protected routes must remain protected

Do not implement a second authentication mechanism.

==================================================

- desktop/laptop width

- conversations can be accessed on mobile

- logout is accessible on mobile
- chat composer remains usable
- no horizontal page overflow is introduced

==================================================
9. SECURITY
==================================================

Any new conversation-title update endpoint must:

- require Firebase authentication
- derive ownership from req.user.uid
- verify the conversation belongs to the authenticated user
- reject unauthorized conversation IDs
- validate the title
- never trust a client-provided userId

Do not weaken any existing ownership checks.

==================================================
10. IMPLEMENTATION PRINCIPLE
==================================================

Prefer extending the existing architecture:

existing auth
→ existing conversation API
→ existing generated client
→ improved responsive UI

Do NOT create:

- duplicate conversation services
- duplicate auth systems
- duplicate APIs
- another database
- another AI title-generation system
- unnecessary state-management libraries

Keep the changes small and interview-friendly.
