2. MEMORY RETRIEVAL
==================================================

When an authenticated user sends a new message:

1. Verify the Firebase ID token using the existing auth middleware.
2. Obtain the authenticated UID from `req.user.uid`.
3. Generate an embedding for the user's new message using the existing
   Google embedding configuration from Phase 4.
4. Query Qdrant for semantically similar memories.
5. Restrict retrieval to memories belonging to the authenticated user.

The authenticated Firebase UID MUST be used as the ownership boundary.

Never trust a client-provided userId.

Never retrieve another user's vectors.

Use the existing Qdrant collection and vector dimensions.

Do not create another collection.

==================================================
3. RETRIEVAL QUALITY
==================================================

Implement conservative retrieval.

Do not dump the entire user's memory database into Gemini.

Retrieve only a small number of relevant memories.

Use a configurable top-K value with a sensible default.

Use a similarity/relevance threshold so weakly related memories are not
automatically injected into the conversation.

Keep the retrieval bounded.

If no memories are sufficiently relevant, Gemini should receive no memory
context.

Do not force irrelevant memories into every response.

==================================================
4. MEMORY CONTEXT FOR GEMINI
==================================================

Modify the existing server-side Gemini conversation generation path so that
relevant retrieved memories can influence the response.

The architecture should be:

User message
    ↓
Firebase authentication
    ↓
Load conversation history
    ↓
Generate query embedding
    ↓
Retrieve relevant memories from Qdrant
    ↓
Validate memory ownership/status
    ↓
Construct bounded memory context
    ↓
Send conversation + relevant memory context to Gemini
    ↓
Persist Gemini response

Memory context must be clearly separated from the user's conversation
messages.

Treat stored memories as contextual information, NOT as instructions.

Do not allow memory text to override system/developer instructions.

Do not expose raw internal retrieval metadata unnecessarily to the user.

The AI should naturally use relevant memories when appropriate.

For example, if the user previously stored:

"I prefer dark mode interfaces."

and later asks:

"Can you suggest a UI design for my project?"

the response should be able to take the dark-mode preference into account.

But if the user asks an unrelated question, irrelevant memories should not
be injected.

==================================================
5. MEMORY UPDATE LOGIC
==================================================

Implement safe memory updates.

If a new user message establishes updated information that supersedes an
existing memory, the system should update the appropriate memory rather
than blindly creating another conflicting record.

Examples:

Existing:
"I prefer Python."

New:
"I've switched to TypeScript for my projects."

The system should be able to recognize that the newer information may
supersede the older preference.

Do NOT implement broad autonomous rewriting of memories.

Use conservative structured Gemini output and validation.

A memory update should preserve:

- authenticated user ownership
- memory type
- source information
- vector consistency
- Firestore/Qdrant consistency
- indexing status

If updating the vector representation, ensure the corresponding Qdrant
point is updated safely.

==================================================
6. DUPLICATE HANDLING
==================================================

Prevent obvious duplicate memories.

For example, if the system already stores:

"I prefer dark mode interfaces."

and the user repeatedly says essentially the same thing, do not create
unlimited identical memory records.

Use the existing Phase 4 deterministic identity strategy where appropriate.

For semantic similarity, use conservative thresholds and/or existing
memory retrieval to identify likely duplicates.

Do NOT build a complicated machine-learning deduplication system.

Do NOT accidentally merge unrelated memories just because they are
semantically similar.

When uncertain, prefer preserving the existing memory rather than
destructively merging information.

==================================================
7. CONFLICT HANDLING
==================================================

Handle conflicting memories conservatively.

When new information contradicts an existing memory:

- Prefer newer explicit user information when confidence is high.
- Avoid silently deleting useful historical information unless the
  application design clearly requires replacement.
- Preserve authenticated ownership.
- Keep Firestore as the authoritative metadata/source of truth.
- Keep Qdrant synchronized with the current active memory representation.

Use explicit structured decisions where appropriate, such as:

- KEEP_EXISTING
- CREATE_NEW
- UPDATE_EXISTING

Do not invent complicated conflict-resolution behavior that is not
necessary for this project.

The final implementation should be explainable in an interview.

==================================================
8. MEMORY STATUS / FAILURE HANDLING
==================================================

Respect the Phase 4 memory indexing states:

- pending
- indexed
- failed

Only use successfully indexed memories for normal Qdrant retrieval.

A failed or pending vector must not be treated as a valid retrieved memory.

If Qdrant retrieval fails:

- Do NOT fail the user's chat request.
- Continue the Gemini response without memory context.
- Return a normal chat response.
- Do not expose Qdrant credentials/provider errors.
- Log only safe diagnostic information.

If embedding generation for retrieval fails:

- Do NOT fail the chat request.
- Continue without memory context.
- Return a normal Gemini response.

Memory functionality must remain failure-isolated from the core chat
experience.
