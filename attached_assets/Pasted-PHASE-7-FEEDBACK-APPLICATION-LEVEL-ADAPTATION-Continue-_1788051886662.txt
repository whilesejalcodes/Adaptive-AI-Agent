PHASE 7 — FEEDBACK + APPLICATION-LEVEL ADAPTATION

Continue from the existing completed Phase 1–6 implementation.

IMPORTANT:
First inspect the actual current codebase and understand the existing architecture.

Do NOT restart or redesign any previous phase.

Phase 1–6 are already implemented and verified:
- React + TypeScript + Vite + Tailwind
- Firebase Authentication
- Firebase Admin authentication
- Firestore conversation/message persistence
- Server-side Gemini generation
- Qdrant + Google embeddings
- Long-term memory creation/storage
- Memory retrieval and management
- Gemini memory context
- Agent orchestration
- Gemini native tool calling
- Owner-scoped memory tools
- Markdown rendering

==================================================
PHASE 7 GOAL
==================================================

Add explicit user feedback and limited application-level adaptation.

The goal is NOT to train or fine-tune Gemini.

The application should use explicit user feedback to improve future behavior for that user in a controlled, explainable way.

Keep this implementation small and interview-friendly.

==================================================
1. INSPECT EXISTING FEEDBACK UI
==================================================

Inspect the existing chat UI.

If thumbs-up / thumbs-down controls already exist, reuse them.

Do not redesign the chat interface.

Determine:
- where feedback is currently displayed
- whether feedback is already stored
- whether an API endpoint already exists
- whether the current message IDs are available to the frontend

Do not create duplicate feedback systems.

==================================================
2. FEEDBACK DATA MODEL
==================================================

Create a minimal Firestore feedback model if one does not already exist.

Use the authenticated Firebase UID as the ownership source.

A logical structure such as:

/feedback/{feedbackId}

with fields such as:

- id
- userId
- conversationId
- messageId
- rating: "positive" | "negative"
- createdAt

Use existing TypeScript types and project conventions where possible.

Do not store arbitrary client-provided userId as the ownership source.

The server must derive ownership from:

req.user.uid

==================================================
3. FEEDBACK API
==================================================

Add an authenticated endpoint for submitting feedback.

Prefer the existing API/router architecture.

For example:

POST /api/messages/:messageId/feedback

or an equivalent route consistent with the current project.

Requirements:

- Verify Firebase authentication.
- Verify that the message belongs to the authenticated user.
- Verify that the conversation containing the message also belongs to the authenticated user.
- Accept only the supported feedback values.
- Prevent unauthorized users from submitting feedback on another user's message.
- Avoid duplicate feedback records for the same user/message unless there is an explicit reason to allow updates.

If feedback already exists, update it rather than creating unlimited duplicate records.

==================================================
4. APPLICATION-LEVEL ADAPTATION
==================================================

Use feedback conservatively.

Do NOT modify or fine-tune the Gemini model itself.

Do NOT train an ML model.

Instead, use explicit feedback to derive small user-specific behavioral preferences where appropriate.

Examples:

Positive feedback:
- indicates the response style/content was useful.

Negative feedback:
- indicates the user was dissatisfied.

However, do NOT automatically convert every thumbs-up/down into a permanent memory.

Feedback should only influence application behavior when there is a clear, validated signal.

Keep adaptation explainable.

For example, a validated preference could influence response-style instructions such as:

- prefer concise explanations
- provide more examples
- explain technical concepts step-by-step

Do not infer sensitive personal attributes.

Do not create hidden personality profiles.

==================================================
5. ADAPTATION STORAGE
==================================================

If adaptation state is required, store it in a small server-owned structure.

Prefer Firestore and the existing authenticated user scope.

Keep adaptation state separate from long-term semantic memories unless there is a strong architectural reason to reuse the existing memory system.

Do not pollute Qdrant with feedback records.

Do not create another database.

==================================================
6. GEMINI INTEGRATION
==================================================

Integrate adaptation into the existing server-side Gemini/agent generation path.

Do not replace the existing agent architecture.

The final generation flow should remain conceptually:

User message
    ↓
Authenticated request
    ↓
Agent
    ↓
Relevant memory/context
    ↓
Validated user adaptation/preferences
    ↓
Gemini
    ↓
Optional tool calls
    ↓
Final response
    ↓
Firestore

Adaptation information must be clearly separated from user-generated memory/context.

Treat stored feedback-derived preferences as application context, not user instructions.

Do not allow feedback data to override system instructions or tool permissions.

==================================================
7. CONSERVATIVE ADAPTATION
==================================================

Do not make the agent aggressively change behavior from one piece of feedback.

Avoid rules such as:

"One thumbs down permanently changes the user's behavior."

Instead, require repeated or sufficiently clear feedback before creating a durable preference.

If the evidence is insufficient, simply store the feedback without changing future behavior.

Make the threshold/configuration easy to understand.

==================================================
8. FEEDBACK UI
==================================================

Reuse the existing thumbs-up/thumbs-down controls.

When the user submits feedback:

- show a small confirmation state
- prevent accidental repeated submissions
- handle loading/error states
- do not expose backend implementation details

Do not redesign the entire chat interface.

==================================================
9. SECURITY
==================================================

Preserve all existing security guarantees.

Never trust:

- client-provided userId
- client-provided ownership
- Gemini-provided userId

All feedback and adaptation data must be scoped to:

req.user.uid

Verify message/conversation ownership before accepting feedback.

Do not expose private feedback or adaptation state to another user.

==================================================
10. FAILURE ISOLATION
==================================================

Feedback must never break normal chat.

If feedback storage fails:

- the existing chat response should remain successful
- show a user-friendly feedback error
- do not retry indefinitely

If adaptation data is unavailable:

- Gemini should still respond normally
- simply omit adaptation context

Do not invent adaptation state.

13. TESTING
==================================================

Actually verify:

A. Positive feedback
- Submit thumbs-up.
- Verify it is persisted.
- Verify duplicate submission is handled safely.

B. Negative feedback
- Submit thumbs-down.
- Verify it is persisted.
- Verify duplicate/update behavior.

C. Adaptation
- Provide enough consistent feedback to trigger the defined adaptation rule.
- Verify the resulting behavior changes as intended.
- Verify insufficient feedback does NOT create a durable preference.

D. Ownership
- User A cannot submit feedback for User B's message.
- Manipulated message/conversation IDs cannot bypass ownership.

E. Failure isolation
- Simulate feedback storage failure if practical.
- Verify normal chat still works.

F. Existing functionality
- Authentication works.
- Conversations persist.
- Messages persist.
- Gemini works.
- Memory retrieval works.
- Agent tool calling works.
- Markdown rendering works.

G. Build
Run:
- frontend typecheck
- backend typecheck
- workspace typecheck
- production Vite build
- backend production build

Do not claim a test passed unless it was actually run.

If something cannot be verified, explicitly state:

"Not verified yet."
