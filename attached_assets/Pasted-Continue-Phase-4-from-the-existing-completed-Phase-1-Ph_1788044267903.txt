User sends message

==================================================

Create a dedicated collection for long-term user memories.

Before creating the collection:

- Determine its actual vector dimension from the SDK/API rather than guessing.
- Use cosine distance unless the embedding API/model specifically requires
  another distance metric.
- Make collection creation idempotent.
- Do not recreate or delete an existing collection unnecessarily.

If the collection already exists, inspect it and reuse it if compatible.

Do NOT silently delete an incompatible collection.

If the existing collection is incompatible, explain the issue before making
a destructive change.

4. EMBEDDING GENERATION
==================================================

Use Google's embedding API through the official Google Gemini SDK/API
already used by the project where possible.

Use a currently supported embedding model.

Do NOT invent a model name.

Inspect the installed SDK/API and use the supported embedding method.

Keep the embedding model configurable through:

GEMINI_EMBEDDING_MODEL

Use a sensible currently supported default if one is required.

Embeddings must be generated SERVER-SIDE.

Never expose embedding credentials or provider configuration to the browser.

The embedding pipeline should:

1. Receive canonical memory text.
2. Generate its vector embedding.
3. Validate that the vector is non-empty and has the expected dimension.
4. Return the vector to the memory storage service.

Do not generate embeddings for ordinary chat messages unless they have first
been selected as actual memories.

==================================================
5. MEMORY EXTRACTION
==================================================

Implement server-side memory extraction.

After a successful user interaction, determine whether the user's message
contains information worth remembering long-term.

Examples of potentially useful memories:

- User preferences
- User interests
- User goals
- Stable personal facts
- Important recurring context
- Explicit instructions about how the assistant should behave

Examples that should generally NOT become long-term memories:

- Temporary questions
- One-off requests
- Generic facts unrelated to the user
- Assistant-generated information
- Random conversational filler
- Information that is clearly temporary

IMPORTANT:

Do not blindly save every user message as a memory.

The extraction system should explicitly decide whether a memory is worth
storing.

==================================================
6. STRUCTURED MEMORY EXTRACTION
==================================================

Use Gemini's structured-output capability if supported by the currently
installed SDK/API.

Do NOT simply ask Gemini to "return JSON" and loosely parse arbitrary text.

The extraction response should follow a typed/validated structure similar to:

{
  "shouldStore": boolean,
  "memories": [
    {
      "text": string,
      "type": string
    }
  ]
}

Use the project's existing validation approach where appropriate.

Validate the generated structure before writing anything to the database.

If the Gemini extraction response is invalid:

- Do not store malformed memory.
- Log only safe diagnostic information.
- Do not crash the chat request.

Keep extraction conservative.

The system should prefer storing fewer useful memories rather than storing
every conversational statement.

- preference

8. FIRESTORE MEMORY STORAGE
==================================================

Create persistent memory metadata in Firestore.

Use a collection such as:

/memories/{memoryId}

Store fields such as:

- id
- userId
- text
- type
- createdAt
- updatedAt
- sourceConversationId
- sourceMessageId

Use Firebase server timestamps where appropriate.

The authenticated Firebase UID must remain the source of truth.

NEVER trust a client-provided userId.

Every memory must belong to:

req.user.uid

Do not allow one user to create or manipulate another user's memory.

==================================================
9. QDRANT MEMORY STORAGE
==================================================

For every accepted memory:

1. Create/obtain its Firestore memory ID.
2. Generate the embedding from the canonical memory text.
3. Store the vector in Qdrant.
4. Store useful payload metadata with the vector.

The Qdrant payload should contain enough information for future Phase 5
retrieval, such as:

- memoryId
- userId
- memory type
- memory text
- source conversation ID
- creation timestamp

CRITICAL:

Every Qdrant point MUST contain the authenticated Firebase UID.

This is required for future user-specific vector filtering.

Never rely only on the Firestore memory ID for ownership.

==================================================
10. FIRESTORE + QDRANT CONSISTENCY
==================================================

Treat Firestore as the persistent source of truth for memory metadata.

Qdrant is the vector-search storage layer.

If Firestore memory creation succeeds but Qdrant storage fails:

- Do not pretend the vector was stored.
- Return a safe diagnostic/result.
- Preserve the Firestore record so the issue can be recovered later.
- Do not expose Qdrant credentials or internal errors to the frontend.

If appropriate, mark the memory with a storage/indexing status rather than
silently losing track of it.

Keep this implementation simple.

Do NOT build a complex background job system in Phase 4.

==================================================
11. WHEN MEMORY EXTRACTION RUNS
==================================================

Memory extraction should happen as part of the existing authenticated chat
flow after a successful user interaction.

Do not run memory extraction:

- on page load
- when loading conversations
- when loading messages
- when refreshing the page
- when navigating between routes

Only process newly received user input.

Avoid duplicate extraction caused by React re-renders or repeated requests.

One user message should not accidentally create multiple identical memory
records because of frontend rendering behavior.

15. ERROR HANDLING
==================================================

Handle failures gracefully.

Potential failures:

- Missing Qdrant configuration
- Qdrant connection failure
- Qdrant collection unavailable
- Gemini extraction failure
- Embedding API failure
- Invalid structured extraction
- Empty embedding
- Embedding dimension mismatch
- Firestore memory write failure

Memory failures must NOT unnecessarily crash an otherwise successful chat
response.

For example:

If Gemini successfully generated the user's response but memory extraction
fails, the user should still receive the Gemini response.

Do not fabricate a memory when extraction fails.

Return safe user-facing errors only where appropriate.

Do not expose raw provider errors.
