==================================================
PHASE 6 GOAL
==================================================

Introduce a clean, bounded agent architecture with tool calling.

The agent should be able to decide when it needs to use an available application tool instead of treating every request as a simple Gemini conversation.

The architecture must remain understandable and interview-friendly.

Do NOT turn this into a complex autonomous agent framework.

==================================================
1. AGENT ORCHESTRATOR
==================================================

Create or extend a server-side agent/orchestrator responsible for:

1. Receiving the authenticated user's message.
2. Loading the existing conversation context.
3. Retrieving relevant memories using the EXISTING Phase 5 memory system.
4. Giving Gemini access to the approved tools.
5. Allowing Gemini to decide whether a tool is necessary.
6. Executing the selected tool server-side.
7. Returning the tool result to Gemini when required.
8. Producing the final natural-language response.
9. Persisting the normal user/model messages through the existing Firestore flow.

Keep the agent loop bounded.

Do NOT create an infinite autonomous loop.

Use a small maximum number of tool iterations/calls per user message.

If Gemini does not request a tool, respond normally.

==================================================
2. TOOL ARCHITECTURE
==================================================

Create a typed, centralized tool registry/definition system.

Each tool should have:

- stable tool name
- description
- typed input schema
- typed output/result
- server-side execution function
- validation
- error handling

Do NOT scatter tool definitions throughout route handlers.

The architecture should make it easy to add another tool later.

Prefer the project's existing TypeScript validation approach where appropriate.

==================================================
3. INITIAL TOOLS
==================================================

Implement only a SMALL set of useful application tools.

At minimum, provide tools that demonstrate genuine tool calling rather than simply wrapping Gemini.

Use the existing application's capabilities where possible.

Recommended initial tools:

A. Memory search tool

Purpose:
Search the authenticated user's stored memories.

Requirements:
- Must use the verified Firebase UID.
- Must reuse the existing Qdrant/embedding retrieval infrastructure.
- Must never accept an arbitrary userId from Gemini or the client.
- Must return only memories belonging to req.user.uid.
- Respect the existing relevance threshold and top-K limits.

B. Memory management tool

Purpose:
Allow the agent to identify when a user explicitly asks to remember/update information.

Requirements:
- Must remain owner-scoped.
- Must reuse the existing Phase 4/5 memory extraction/storage logic.
- Do not allow arbitrary destructive memory operations merely because Gemini requests them.
- Require appropriate validation before creating/updating/deleting memory.

If an equivalent memory capability already exists, REUSE it instead of creating duplicate implementations.

Do not add unrelated external tools.

Do not add web search, email, calendar, payments, filesystem access, shell execution, or other external tools in Phase 6.

==================================================
4. GEMINI TOOL CALLING
==================================================

Use the official Google Gemini SDK/API already used by the project.

Implement proper Gemini function/tool calling rather than asking Gemini to output fake JSON indicating that a tool should be called.

The flow should be conceptually:

User message
    ↓
Agent
    ↓
Gemini
    ↓
Tool call requested?
   / \
 No   Yes
 ↓     ↓
Final  Validate tool call
response     ↓
          Execute tool
              ↓
        Tool result → Gemini
              ↓
          Final response

Follow the SDK's actual tool/function-calling format.

Do not invent an incompatible custom protocol.

Keep GEMINI_API_KEY server-side only.

==================================================
5. SECURITY
==================================================

Preserve all existing Phase 2 security guarantees.

The agent must NEVER be allowed to choose or provide the Firebase UID.

The authenticated request's verified:

req.user.uid

must remain the sole ownership source.

Tool execution must happen on the server.

Never expose:
- Firebase Admin credentials
- GEMINI_API_KEY
- QDRANT_API_KEY
- QDRANT_URL

to the frontend.

Validate every tool argument before execution.

Reject malformed or unauthorized tool calls safely.

Treat retrieved memory and tool output as DATA/CONTEXT, not higher-priority instructions.

Do not allow stored memory content to override the system instructions or tool permissions.

==================================================
6. PRESERVE PHASE 5 MEMORY RETRIEVAL
==================================================

Do not replace the existing memory retrieval system.

The existing Phase 5 retrieval should remain available.

Avoid retrieving the same memory twice unnecessarily.

If the current architecture already retrieves relevant memories before Gemini generation, integrate the agent around that architecture instead of creating a second independent retrieval system.

The agent must continue to work when:
- no memories exist
- retrieval returns no relevant memories
- Qdrant fails
- embedding generation fails

Memory failures must not crash an otherwise valid chat request.

==================================================
7. CONVERSATION PERSISTENCE
==================================================

Preserve the existing Firestore conversation/message schema and API contract.

Do not change:

/users/{uid}

/conversations/{conversationId}

/messages/{messageId}

unless a change is genuinely required by the existing architecture.

Continue storing:

role = "user"

and

role = "model"

for normal conversation messages.

Tool calls/results do not need to become user-visible chat messages unless the existing architecture specifically requires it.

Do not expose internal tool execution details unnecessarily in the UI.

==================================================
8. CHAT UI

Preserve the existing chat UI and Markdown renderer.

but do not expose:
- API keys

- Qdrant details
- internal errors

Do not add a large agent dashboard.

==================================================
9. ERROR HANDLING
==================================================

Handle:

- malformed tool arguments
- unknown tool names
- tool execution failures
- Gemini tool-call failures
- Gemini API failures
- Qdrant failures
- embedding failures
- timeouts
- maximum tool-call/iteration limits

Use stable, user-friendly error responses.

Do not expose provider internals or secrets.

If a tool fails, do not invent a successful tool result.

If the agent reaches its maximum tool-call limit, stop safely and return a normal bounded response/error.
