5. FIRESTORE DATA MODEL
==================================================

Before implementing Firestore operations, explain the proposed schema.

At minimum support:

users
conversations
messages

A sensible conceptual structure is:

users/{userId}

conversations/{conversationId}

messages/{messageId}

or an equivalent structure if the existing architecture makes another
design more appropriate.

Every conversation and message must be associated with the authenticated
user.

Messages should also identify their conversation.

At minimum, messages should support:

- message ID
- conversation ID
- user ID
- role
- content
- created timestamp

Conversations should support appropriate fields such as:

- conversation ID
- user ID
- title
- created timestamp
- updated timestamp

Use the existing shared TypeScript types where appropriate.

Do not introduce unnecessary database duplication.

==================================================

- User B's conversations
- User B's messages
- User B's user data

Do not rely only on frontend checks.

Use Firebase Authentication identity and appropriate Firestore security
rules.

The authenticated Firebase UID must be the source of truth.

Do not accept arbitrary user IDs from the client and trust them.

If the backend receives a userId from the client, do not use it as the
authority for ownership.

==================================================
8. FIRESTORE SECURITY RULES
==================================================

Create appropriate Firestore security rules.

Rules should enforce that:

- Only authenticated users can access protected user data.
- A user can only read/write their own user data.
- A user can only access their own conversations.
- A user can only access their own messages.
- A user cannot manipulate another user's userId to gain access.

Keep the rules understandable and maintainable.

Do not mark security as complete merely because rules were written.

Test the ownership behavior.
