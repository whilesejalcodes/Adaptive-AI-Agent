==================================================
CORE CONCEPT
==================================================

The application is an adaptive personal AI agent.

The agent should not simply save every conversation.

It should intelligently determine whether information is:

1. Temporary information
2. A useful long-term fact
3. A user preference
4. A user goal
5. A project or skill
6. A correction
7. An update to existing information
8. Irrelevant information that should not be stored

Example:

User:
“I am preparing for SDE interviews.”

The system should identify this as potentially useful long-term information.

Later:

User:
“I finished React and now I’m focusing on backend.”

The system should be able to update relevant memory rather than blindly
creating duplicate memories.

Another example:

Existing memory:
“User prefers concise explanations.”

New message:
“From now on, I want detailed explanations.”

The system should recognize the conflict and update the relevant memory.

==================================================
IMPORTANT DEFINITION OF “SELF-LEARNING”
==================================================

Do NOT claim that the underlying Gemini model is being retrained.

This project should implement application-level adaptation.

The agent “learns” by:
- storing useful memories
- retrieving relevant memories
- updating outdated memories
- incorporating explicit user feedback
- adapting future responses based on these memories

The README and UI should describe this accurately as:
“adaptive/self-improving behavior through persistent memory and feedback”

rather than claiming model retraining.

==================================================
AI AGENT
==================================================

Create a dedicated agent layer.

Do NOT put Gemini API calls directly inside React components.

The agent should perform a workflow similar to:

1. Receive authenticated user message
2. Retrieve relevant memories
3. Build a controlled context
4. Determine whether tools are needed
5. Call tools if appropriate
6. Generate the response
7. Determine whether new information should become memory
8. Create/update memory if appropriate
9. Store conversation data
10. Return the final response

Keep responsibilities modular.

Possible functions/modules include:

- generateResponse()
- retrieveMemories()
- classifyMemory()
- createMemory()
- updateMemory()
- deleteMemory()
- detectMemoryConflict()
- executeTool()
- processFeedback()

Use strong TypeScript types.

Avoid unnecessary use of `any`.

==================================================
MEMORY EXTRACTION
==================================================

When appropriate, the AI should determine whether a user message contains
information worth remembering.

For example:

“I ate pizza today.”

Probably not worth permanent memory.

“I am preparing for SDE interviews.”

Potentially worth remembering.

“I prefer concise explanations.”

Worth remembering.

“I prefer detailed explanations now.”

Potentially an update to an existing preference.

Use structured output from Gemini where appropriate so that the application
can reliably interpret the memory decision.

The structured result should contain information such as:

- shouldRemember
- memoryType
- memoryText
- importance
- possibleExistingMemoryToUpdate
- reason

Do not rely on fragile string parsing if structured output can be used.

==================================================
MEMORY RETRIEVAL
==================================================

Before generating a response:

1. Convert the relevant query/context into an embedding.
2. Search Qdrant.
3. Restrict results to the authenticated user’s memories.
4. Retrieve only the most relevant memories.
5. Apply a similarity threshold.
6. Limit the number of memories included in the prompt.
7. Add only relevant memories to the agent context.

Do NOT send every stored memory to Gemini.

Use configurable values for:

- top-K memories
- similarity threshold
- maximum memory context size

These should be easy to change later.

==================================================
API COST AND EFFICIENCY
==================================================

This is VERY IMPORTANT.

Design the system to minimize unnecessary Gemini API calls from the beginning.

The application should be designed to work comfortably within a reasonable
free-tier API quota during development and personal use.

Requirements:

1. Do not call Gemini for tasks that can be handled deterministically with
normal application code.
2. Do not use Gemini to search vector memory.
Use Qdrant similarity search.
3. Do not generate embeddings unnecessarily.
4. Do not embed every meaningless user message.
5. Only create/update long-term memory when appropriate.
6. Avoid unnecessary sequential Gemini calls.
7. Prefer structured outputs so that one appropriate Gemini call can provide
both the response and machine-readable metadata when practical.
8. Do not send the entire conversation history to Gemini unnecessarily.
9. Retrieve only the most relevant memories.
10. Keep prompts concise.
11. Limit context size.
12. Cache appropriate deterministic/reusable results.
13. Implement rate-limit handling.
14. Implement retry with exponential backoff where appropriate.
15. Gracefully handle API failures.
16. Keep the Gemini integration behind a modular service interface so the
model can be changed later without rewriting the application.
17. Do not sacrifice correctness or maintainability merely to reduce API
calls.

The goal is efficient architecture, not hacks.
